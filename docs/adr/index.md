Architecture Decision Records - why the codebase is the way it is.

Every page is a draft. "Accepted" in a page means the project owner chose it; "Proposed" means it waits for their decision.
Supersede an accepted ADR rather than editing it.

# Concepts
* [ADR 0001: Record architecture decisions](0001-record-architecture-decisions.md) - Decisions that are expensive to reverse are written as numbered ADRs in this folder.
* [ADR 0002: Minimum iOS 18, iOS 26 styling isolated in the Design System](0002-ios-18-minimum-ios-26-styling.md) - The app deploys to iOS 18 and adopts iOS 26 Liquid Glass only inside the DesignSystem package.
* [ADR 0003: Use the Matrix Rust SDK through its Swift package](0003-matrix-rust-sdk.md) - The app is built on matrix-rust-sdk's Swift bindings, which requires sliding sync on the homeserver.
* [ADR 0004: SwiftUI with Observable view models and coordinators](0004-swiftui-observable-coordinators.md) - Screens are SwiftUI views driven by one @Observable view model each; coordinators own navigation.
* [ADR 0005: Layers as local Swift packages](0005-layered-local-swift-packages.md) - Features, Domain, MatrixData, DesignSystem and AppShared are separate local packages so import rules are compile errors.
* [ADR 0006: The Matrix SDK is reached only through proxy protocols](0006-sdk-behind-proxy-protocols.md) - MatrixData wraps each SDK object in a proxy that implements a Domain protocol; no SDK type leaves that package.
* [ADR 0007: One session store shared by the app and the extension](0007-shared-session-store-app-group.md) - The SDK store lives in the App Group container and tokens in a shared Keychain group, read by both processes.
* [ADR 0008: Sign in with SSO after server discovery](0008-authentication-sso-and-discovery.md) - The app discovers the homeserver from its well-known document and signs in through the system web authentication session.
* [ADR 0009: Push through the existing gateway, decrypted in the extension](0009-push-gateway-and-nse-decryption.md) - The app registers an APNs pusher on the homeserver via the Twake push gateway; the extension fetches and decrypts the event.
* [ADR 0010: Test logic with fakes and UI on both iOS versions](0010-testing-strategy-two-ios-versions.md) - View models and use cases are unit-tested against fake proxies; shared components are checked on iOS 18 and iOS 26 simulators.
* [ADR 0011: Version 1 is core chat only](0011-v1-scope-core-chat.md) - v1 ships sign-in, chat list, timeline, encryption recovery and push; every other Flutter feature is deferred. To be superseded by ADR 0026 (Proposed).
* [ADR Template](_template-adr.md) - Copy this when recording an architecture decision.
* [ADR 0012: Reuse the Flutter app's bundle identifier](0012-reuse-flutter-bundle-identifier.md) - The native app ships as app.twake.ios.chat, so it installs over the Flutter app instead of beside it.
* [ADR 0013: Port behaviour from one pinned Flutter commit](0013-flutter-baseline-and-feature-status.md) - Proposed: behaviour is ported only from twake-on-matrix origin/main at 5a3e9e849; every Flutter feature is marked kept, deferred or dropped.
* [ADR 0014: CI on GitHub Actions with GitHub-hosted macOS runners; swift-format for formatting and lint](0014-ci-github-actions-swift-format.md) - CI runs on GitHub Actions macOS runners like the Flutter app, and swift-format from Xcode formats and lints; billed macOS minutes are the price.
* [ADR 0015: Pin matrix-rust-components-swift at exactly 26.04.01](0015-pin-matrix-rust-components-swift-26-04-01.md) - The SDK package is pinned to 26.04.01, the version the Flutter app's extension uses; it is older than Element X, so API names come from the pinned package.
* [ADR 0016: Choose the licence and the reuse rule for code from other clients](0016-source-licence-and-reuse-rule.md) - Either relicense to AGPL-3.0 and port with attribution, or stay MIT and reimplement clean-room, reusing only the Apache-2.0 Element X snapshot.
* [ADR 0017: What the native app keeps from the Flutter app and what it deletes](0017-flutter-upgrade-keep-and-drop-lists.md) - Proposed: lists the identifiers and server contracts the update keeps unchanged and the Flutter stores the first-launch cleanup deletes.
* [ADR 0018: Prove v1 behaviour with unit, snapshot and manual checks](0018-behaviour-oracle-for-v1.md) - Proposed: each v1 area names its oracle; unit and snapshot tests gate every pull request, a manual QA script gates each TestFlight build, and no end-to-end suite is required in CI for v1.
* [ADR 0019: Offer password login in Debug builds only](0019-password-login-debug-builds.md) - Debug builds sign in with m.login.password against the staging homeserver behind #if DEBUG; Release stays SSO-only as ADR 0008 says. Superseded by ADR 0021.
* [ADR 0020: Integration tests against staging are opt-in and local only](0020-opt-in-local-staging-integration-tests.md) - Integration tests read staging credentials at run time from a local env file or environment variables, skip when they are absent, and never run in CI.
* [ADR 0021: Sign in exactly as the Flutter app does](0021-sign-in-as-the-flutter-app.md) - TwakeWelcome first; Twake ID through the registration site, company servers through discovery, SSO via the web session and the loginToken; password only on a server without SSO, in every build.
* [ADR 0022: Lay out by the Flutter app's width breakpoints](0022-adaptive-layout-flutter-breakpoints.md) - Under 905 pt wide the app shows one column; from 905 pt the 472 pt chat list sits beside the chat, as twake-on-matrix ResponsiveUtils does, so phones, a folded and an unfolded Duo and iPads share one rule.
* [ADR 0023: Take features from the Twake Chat web client; design the experience after the best messengers](0023-features-from-web-client-ux-from-best-messengers.md) - Proposed: what the iOS app does comes from linagora/twake-space-chat; how it looks and feels is decided here after iMessage, Telegram and WhatsApp, with Apple's components. Supersedes ADR 0013.
* [ADR 0024: Keep the recovery key on ToM so a new device unlocks itself](0024-recovery-key-kept-by-tom.md) - Proposed: after sign-in the app reads the recovery key from ToM's /_twake/recoveryWords and verifies the device with it, or sets encryption up and gives ToM the new key; whoever controls ToM can read the encrypted history.
* [ADR 0025: No comments in Swift code](0025-no-comments-in-code.md) - Proposed: Swift files hold no comments at all, doc comments included; the reason behind the code lives in an ADR or the knowledge base, and scripts/check-no-comments.sh fails on any comment.
* [ADR 0026: A Matrix-first client; every non-Matrix server feature is detected, never assumed](0026-matrix-first-client-server-features.md) - Proposed: the app aims at full parity with twake-on-matrix and twake-space-chat on any Matrix homeserver; each feature that needs a Twake or other service is turned on only when the server announces it, and is hidden on a plain Synapse. Supersedes ADR 0011's v1 scope once accepted.
* [ADR 0028: GIFs through twake-common-proxy, stickers from image packs, checklists off until defined](0028-gifs-stickers-checklists.md) - Proposed: the GIF picker calls twake-common-proxy with an OpenID token and shows only when a proxy URL is built in and the proxy offers GIFs; stickers come from MSC2545 image packs; checklists stay off until the web defines an event format.
* [ADR 0030: Verify devices with emoji only until the SDK exposes QR verification](0030-qr-device-verification-disabled-until-sdk.md) - Proposed: QR device verification stays off because no matrix-rust-components-swift release exposes it; emoji verification stays the only method, and the missing FFI API is a candidate upstream contribution. The personal QR code and the QR scanner are built without the SDK.
* [ADR 0031: Mark chat list rows from what the SDK syncs, and read presence only when a row shows](0031-chat-list-row-marks.md) - Proposed: a direct chat's presence dot is read with one request when its row shows, at most once a minute per person, never on a timer, because the pinned SDK syncs no presence.
* [ADR 0029: Find and invite people by e-mail or phone through the account's identity server](0029-identity-server-for-email-and-phone.md) - Proposed: lookups, phone-contact matching and third-party invites use the identity server named by account data or .well-known (ToM on Twake), only after the user accepts its terms and only with sha256 hashes; hidden without one.
* [ADR 0038: Make calls in the app with the Element Call widget, offered only on a server with a LiveKit token service](0038-in-app-calls-with-element-call-widget.md) - Proposed: in-app calls run Element Call in a web view driven by the SDK's widget driver, as Element X does; they appear only when the well-known names a LiveKit token service (livekit_service_url), otherwise the Meet link of #92 stays. CallKit reports the call; ringing an incoming call in the background is left for later.
* [ADR 0039: Several accounts, one store and one Keychain item each, one account on screen](0039-multiple-accounts.md) - Proposed: each account gets its own SDK store directory and Keychain item, listed in an accounts file in the App Group; the signed-in single account stays where it is; pushes find their account by the client identifier they already carry; one account runs on screen, the others reach the user through push.
* [ADR 0036: Create spaces and keep chat folders as the web and Flutter do](0036-spaces-and-folders-in-the-chat-list.md) - Proposed: spaces and sub-spaces are created with the web's /createRoom body; chat folders use the shared app.twake.chat.folders account data and u.<name> room tags; the public page link stays off; the chat preview opens from its menu.
* [ADR 0037: Keep contacts in the ToM address book and invite through ToM when the server enables it](0037-tom-address-book-and-invitations.md) - Proposed: with t.server the Contacts tab lists, adds, renames and removes ToM address book contacts; with enable_invitations phone contacts are invited through ToM and a sign-up link can be shared; status read from ToM, nothing stored.
